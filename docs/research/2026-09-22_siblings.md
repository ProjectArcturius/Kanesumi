### 1.2 三条能立刻落地的结论

1. **`MetroTextBox::filled()` 极简变体：建议加，且依据比原以为的更强。**
   `SECA_SYNC` §Ⅲ-1 把这条列为「待裁定」（`docs/SECA_SYNC_2026-09-22.md:209`）。
   本次从调用方侧补齐了证据：Sakichan **三处输入框全部**走的就是填充式形态
   （`ConnectionScreen.kt:105`、`SettingsScreen.kt:70`、经 `MetroChatInputBar.kt:61`），
   而 Rust 侧 `MetroTextBox` 头部即声明「**单行**文本输入框」且**只有一种形态**（1px/2px 边框，
   `text_box.rs:1,26,169-171`）。⇒ 不是「可加可不加」，是**真实用例三缺一**。

2. **发送键门控：照搬会引入功能死路，必须改设计。**
   sec-a 的 `MetroChatInputBar` 把门控**硬编码**为 `enabled && text.isNotBlank()`
   （`MetroChatInputBar.kt:73`），而 Sakichan 把「发送」在任务运行时**换成「中止」**
   （`ChatScreen.kt:102`）⇒ 输入框为空时 `active == false` ⇒
   `MetroIconButton(enabled=false)` 的 `clickable` 被**自动断开**
   （`MetroIconButton.kt:31`）⇒ **空输入时中止按钮不可点**。
   Rust 侧**不得**照搬这条门控；应改为调用方传入的 `send_enabled` 策略。详见 §2.5。

3. **`ControlKind` 里有 4 个「幽灵控件」。**
   `kanesumi-controls/src/lib.rs:133-146` 的枚举声明了 `MetroDivider` / `MetroBottomSheet` /
   `MetroProgressIndicator` / `MetroListRow`，但**全仓无实现、无 `pub use`**
   （四者仅出现在 `lib.rs:137,139,144,145,154,156,161,162`，均为枚举本体）。
   其中 **`MetroDivider` / `MetroBottomSheet` / `MetroProgressIndicator` 在 sec-a 都真实存在**
   （`MetroDivider.kt:21`、`MetroBottomSheet.kt`、`MetroProgressIndicator.kt`）。
   ⇒ 这不是笔误，是**移植欠账被写进了枚举**。详见 §4.4。

### 2.5 ⚠ 本轮推翻/修正 `SECA_SYNC` §Ⅲ 的两处结论

`docs/SECA_SYNC_2026-09-22.md` §Ⅲ 是从 **sec-a 侧**读的，本次从**调用方侧**读，有两处需要更新：

#### 修正 1：发送键门控——「唯一可直接翻译的策略」**不可直接翻译**

`SECA_SYNC_2026-09-22.md:97-98` 写道：
> 3. **发送键硬门**：`enabled && text.isNotBlank()` + 图标/文字双形态（`MetroChatInputBar.kt:73-91`）
>    —— **唯一可直接翻译的策略**。

**本次发现该门控在其唯一下游即已导致功能死路。** 证据链：

1. `MetroChatInputBar.kt:73` — `val active = enabled && text.isNotBlank()`
2. `ChatScreen.kt:102` — 任务运行时 `onSend` 被替换为 `onAbort`（图标同时换成 `Icons.Filled.Close`）
3. `MetroIconButton.kt`（sec-a，KDoc 明写）：
   > `enabled = false 时 clickable 自动断开,视觉衰减由调用方在 content 里处理`
   实现即 `clickable(enabled = enabled, onClick = onClick)`（`MetroIconButton.kt:31`）
4. ⇒ **输入框为空 + 任务运行中** ⇒ `text.isNotBlank() == false` ⇒ `active == false` ⇒
   **「中止」按钮不可点**。用户此时唯一想做的事恰好是做不了的。
5. 交叉印证：`ChatViewModel.abort()`（`ChatViewModel.kt:163-184`）实现完整
   （取消两个 job、停前台服务、清 pending store、通知 serve 端 abort），
   **不是**死代码 —— 只是**入口在空输入时被门控掐断**。

**对 Rust 侧的指令**：门控是**产品策略**，不是控件策略。
`MetroChatInputBar` 把「什么算可发送」写死在控件里，等于让控件替调用方做产品判断。
Rust 侧若移植，**必须**把门控外提为参数（如 `send_enabled: bool` 或
`SendGate` 策略），让「运行时发送键变中止键」这类用例仍然可达。
> 这是本轮对 Kanesumi 最有价值的一条：**它是一条「反向教训」，不是「可抄的优点」。**

#### 修正 2：`MetroTextField` 并非「只有 `MetroChatInputBar` 一个调用者」

`SECA_SYNC_2026-09-22.md:84-85` 称：
> **并且 `MetroTextField` 在 sec-a 是死代码**：唯一调用者是 `MetroChatInputBar.kt:61`

该句**限定在 sec-a 仓内是对的**（sec-a 内确为死代码），但**跨仓读会误导**：
Sakichan 仓内 `MetroTextField` 另有**两处独立调用**
（`ConnectionScreen.kt:105`、`SettingsScreen.kt:70`），且都是 `singleLine = true` 的
**独立表单用法**，不经 `MetroChatInputBar`。
⇒ 结论应从「死代码 / 无实战」修正为：
**「sec-a 内无调用者，但下游两个真实应用在用，共 3 个调用点、2 种形态（单行表单 + 多行聊天）」**。
这直接加强了 §1.2 第 1 条（`filled()` 变体）的必要性。
