## §1 结论先行

### 1.1 最重要的发现：这次的「不舒服」不是 Kanesumi 造成的

**arc-deck 的 Rust 侧根本没有用 Kanesumi。**

| 检验 | 结果 | 证据 |
|---|---|---|
| `arc-deck/kanesumi/crates/arc-deck-shell/Cargo.toml` 有无 kanesumi 依赖 | **无**（只有 `windows-sys`） | `arc-deck/kanesumi/crates/arc-deck-shell/Cargo.toml:9-12` |
| `arc-deck/Cargo.lock` 出现 `kanesumi` 字样 | **0 次**（lock 里只有 `arc-deck-shell` / `ime-probe` / `layout-bench` + fontdue/rustybuzz 等） | `arc-deck/Cargo.lock`（全文件） |
| 有无 git submodule | **无 `.gitmodules`** | `Test-Path arc-deck/.gitmodules` → False |
| `arc-deck/kanesumi/` 是什么 | **只是 Rust 变体的目录名**，不是 Kanesumi 的 submodule / 检出 | `arc-deck/Cargo.toml:8-12`（workspace members 直接指向 `kanesumi/crates/arc-deck-shell`） |
| 有没有 `[patch]` 指向本地 Kanesumi | **无**（全仓 4 个 Cargo.toml 均无 `[patch]`） | `arc-deck/Cargo.toml` / `kanesumi/crates/arc-deck-shell/Cargo.toml` / `probes/*/Cargo.toml` |

arc-deck 自己的文档也写着同一件事：`docs/ARCHITECTURE.md:25-27` 说 Scene / SceneCommand / App /
TextEngine 是**「刻意镜像」** Kanesumi 的对应物，「将来若要直接消费上游…替换是无痛的」——
即**接入是未执行的计划，不是已发生的事实**。`docs/ARCHITECTURE.md:143-149` 的「后续」清单里
第 4、5 条正是「接入 `kanesumi-canvas` 的 `TextEngine`」「接入 `kanesumi-controls`（48 个控件）」。

**因此「C# 更舒服」的主要成因不是 Kanesumi 缺什么，而是 Rust 侧是一个 2,735 行的骨架，
且它把框架层该做的事全留成了缺口。** 下面按贡献排序。

### 1.2 「更舒服」的成因排序（前三名）

**第一名：C# 的布局由平台算，Rust 侧根本没有布局层 —— 而不是「布局层不好用」。**

C# 侧一个屏幕的全部几何来自 XAML 声明：`Grid.RowDefinitions` 的 `Auto` / `*` 让输入区永远贴底
（`uwp/src/ChatPage.xaml:224-229`、`ChatPage.xaml:330`），栏宽固定 + 剩余吃满
（`uwp/src/ToolsPage.xaml:21-25`），行内排布靠 `StackPanel Spacing`
（`uwp/src/SessionsPage.xaml:212-213`）。**没有一处 `Left/Top/Width/Height` 是App 算的。**

Rust 侧没有布局引擎，坐标是 App 手写算术，且**全是字面量**：
`kanesumi/.../bin/arc-deck-demo.rs:112-113`（`pad = 24.0` 起点）、`:130`（`y += 46.0`）、
`:135`（`y += 34.0`）、`:175`（`y += 44.0 + 18.0`）、`:215`（`y += btn_h + 22.0`）；
横向同理 `:181`（`Rect::new(pad, y, btn_w, btn_h)`）、`:206`
（`Rect::new(pad + btn_w + 12.0, y, btn_w, btn_h)`）。一个控件的 y 由**上一条语句的累加结果**决定 ——
改动任何一项高度都要顺次改后面所有数字。`DESIGN_SYSTEM.md:159` 自己把这条列为要反着做的反面：
「显式命名的矩形，而非测量」。

> **注**：这不是「Kanesumi M2 没做」。`kanesumi-canvas/src/layout.rs` 是 774 行的真约束
> Constraints / Measure / Arrange 引擎（见 §5.1）。问题是 Rust 侧**没有接入它**。

**第二名：控件不存在，且五个屏幕在 Rust 侧对应零个。**

C# 侧是 6 个页面（`Get-ChildItem uwp/src -Filter *Page.xaml` → ShellPage / SessionsPage /
ChatPage / WorkspacesPage / ToolsPage / SettingsPage），每页都有完整功能。Rust 侧只有
**一个 demo 窗口**（`bin/arc-deck-demo.rs`），它是 IME 通路验证载体，不是应用。

对照两侧真正「写出来」的规模（逐字节统计，两口径）：

| | 文件数 | 总行 | 纯注释行 | **代码行（去纯注释）** | 屏幕数 |
|---|---:|---:|---:|---:|---:|
| C# `uwp/src`（`.xaml` + `.cs`，不含 obj/bin） | 24 | 3,260 | 449（14%） | **2,811** | **6** |
| Rust `arc-deck/kanesumi`（`.rs`） | 12 | 2,735 | 539（20%） | **2,196** | **1** |

**Rust 侧花了 C# 侧 78% 的代码量，做出了 1/6 的屏幕。**（换算：每屏代码行 C# 469 vs Rust 2,196。）

> **口径说明**：「纯注释行」只统计**整行都是注释**的行（`//` / `///` / `<!--` 开头），
> 不含行尾注释，也不扣除空行（另有约 16% 空行）。两侧注释密度差别不大（20% vs 14%），
> **所以「Rust 代码量少是因为注释多」这个直觉不成立** —— 见 §6-5。

Rust 侧那 2,196 行的去向也说明问题：`platform/mod.rs` 715 行几乎全是 Win32/IMM32 消息翻译
（`WM_IME_*` 三个分支占了 `:353-447` 共 95 行），`ime.rs` 242 行是纯逻辑状态机 ——
**这些是「外壳」与「平台适配」，不是 UI**。真正画界面的只有 demo 的 295 行**（其中 `render()` 约 135 行）**。

**第三名：平台免费给的三件事，Rust 侧分别是「没有」「空实现」「占位」。**

| 能力 | C# 侧 | Rust 侧 |
|---|---|---|
| 文本量测 | 平台字体引擎按真实字形算宽，`TextTrimming="CharacterEllipsis"` + `MaxLines` 声明式 | **宽度量测全是启发式**：`HeuristicTextEngine` 按字号线性估算（`app.rs:73-101`，LATIN 0.55 / CJK 1.0）；GDI 路径更直接：`宽度 = 字符数 × 字号 × 0.9`（`platform/mod.rs:295`）。**渲染用的是真字体**（`platform/mod.rs:290` `GetStockObject(DEFAULT_GUI_FONT)` + `TextOutW` `:301`），即**量测与渲染宽不一致**（见下） |
| 裁剪 | 每个 `ScrollViewer` / 控件模板自带 | `apply_clip()` **空实现**（`platform/mod.rs:270`），`PushClip`/`PopClip` 画不出任何效果 |
| 滚动 | `ScrollViewer` 一行 | 事件能收到（`platform/mod.rs:541-551`），demo **零处理** |
| 重绘范围 | 平台按失效区域自动算 | `InvalidateRect(hwnd, null(), 0)` —— **NULL 矩形 = 整窗失效**（`platform/mod.rs:84`，全仓唯一一次调用），无任何脏矩形计算 |

这三条各自都足以造出「看起来能用、实际不对」的界面 —— 而那正是「手感」的来源。

> **一条比上述三条更锋利的缺陷（独立复核发现）**：Rust 侧**同时持有两套互不相容的宽度模型**。
> App 用 `HeuristicTextEngine` 定位光标与组合串下划线（`bin/arc-deck-demo.rs:156`、`:159`），
> 而渲染器用 `0.9 × 字号 × 字符数` 定位 Center/Right 对齐（`platform/mod.rs:295`）。
> **于是「居中」的文本并不是按 App 自己认定的宽度居中的** —— 这类偏差在静态阅读时看不出来，
> 在屏幕上表现为「差一点点」，正是最难归因、也最容易被读成「框架不行」的那种不适。

### 1.2.1 最能说明问题的一组数字

「平台免费给」的规模，可以用**两侧各自手写的交互基础设施代码量**来量：

| | C# 侧 | Rust 侧 |
|---|---|---|
| 手写焦点 / 键盘代码 | **2 处**（`ChatPage.xaml.cs:43` 一次 `Focus()`、`:89` 一个 `KeyDown`） | **0 处**（`Key::Tab` 有变体但无人消费，`:278` 落入 `_ => {}`） |
| 手写交互反馈（hover/press 视觉状态） | **0 处**（`.xaml` 里 `VisualStateManager`/`Storyboard` **0 命中**） | 1 处硬切（`bin/arc-deck-demo.rs:185-192`） |
| 手写滚动 | **0 处** | **0 处**（但有缺口：事件到了没人处理） |
| 手写布局/坐标算术 | **0 处**（全部 `Grid` 的 `Auto`/`*`） | 1 屏 **45 行**（demo `:112-215`） |
| 手写文本溢出处理 | **4 处 `TextTrimming` + 5 处 `MaxLines`**（声明式） | **0**（`SceneCommand::Text` 连宽度字段都没有，`scene.rs:164-170`） |
| 手写文本量测 | **0 处** | **2 套互不相容的模型**（`app.rs:73-101` 启发式 vs `platform/mod.rs:295` `0.9×字号×字符数`） |

**C# 侧用 2 行焦点代码 + 0 行布局代码，得到了 6 个屏幕的完整键盘与自适应行为。
Rust 侧用了 45 行坐标算术 + 0 行焦点代码，得到 1 个屏幕且无法用键盘操作。**
这个不对称就是「更舒服」的可核对内核。


### 1.3 一句话回答

> **Rust 侧不成熟，但「用的是 Kanesumi 且它不成熟」这个前提不成立。**
> 真实情况是：Rust 侧是一个**自研骨架**，它**主动选择**先把 Scene 契约与 IME 打通、
> 把布局/控件/裁剪/滚动留作缺口，并计划日后再接 Kanesumi。
> 「C# 更舒服」的排序是：**① 无布局层（手写坐标）→ ② 无控件库（1 屏 vs 6 屏）→
> ③ 文本/裁剪/滚动三项平台基础设施在 Rust 侧是缺口**。
> 前两条里，Kanesumi **已经有实现**（§3、§6）；第三条部分已在 M0/M1 落地。

## §2 arc-deck 结构速览

### 2.1 它是什么应用

**DeepSeek Harness（DSH）的原生桌面客户端** —— 不是 WebView 壳，这是项目立项的**唯一理由**：
`README.md:56`「Arc Deck 走第三条路：**没有 WebView**」；`:45-54` 给出动机实测
（Electron 壳的 Chromium ≈1.0 GB + 1,937 秒 CPU，可省）。设计语言基于 Kanesumi Design
（`README.md:60-66`，正典指向 Ether monorepo `docs/KANESUMI_DESIGN.md`）。

### 2.2 三个目录，不是两个

`AGENTS.md:6-10` 说明真实结构是**三块**：

```
kanesumi/       Rust + 自绘 Scene（跨平台）        ← workspace 管
uwp/            C# + WinUI 2（Windows 专属）       ← MSBuild 管
arc-deck-dsh/   协议客户端（C# / .NET 9 桌面进程）  ← 两个实现共用
```

**协议层是共用的，界面层不共享**（`AGENTS.md:12`：「两个实现代码不共享，外观也不共享」）。
`arc-deck-dsh` 是本仓唯一「已实测跑通」的完整功能面：`AGENTS.md:800-812` 记录它已能
找到内核 → 起 `dsh --profile sdk` → 握手 → `session/prompt` → 流式事件 → 投影助手正文，
并在 73 个真实会话上逐块对账（71 通过 / 0 不一致）。

### 2.3 两侧实现对照：**不是一一对应，是各有侧重且极不对称**

## §3 逐项对照表

**读法**：每项给「需求 / C# 做法+行号+行数 / Rust 做法+行号+行数 / 差距性质」。
「差距性质」只有三类：
- **引擎缺口** —— 框架该提供的能力不存在（Kanesumi 需要补）；
- **接入缺口** —— 能力存在/上游有，但这一侧没接（工程动作，不是框架问题）；
- **平台缺口** —— 依赖 OS 提供，自绘路线必须自己造（Kanesumi 路线上的长期成本）。

### 5.2 Rust 侧真正更好 / 更可控的地方

**(a) IME 通路是真的打通了，而且被测试钉死 —— C# 侧「免费得到」，但没得到更多。**

Rust 侧 `ime.rs` 是 242 行纯逻辑状态机，四条不变量各有测试（`ime.rs:20-24`）：
组合串永不进文档 / 提交串是唯一 `Commit` 来源 / 重新组合清空不累积 / 取消组合不提交。
另有一条真实陷阱被钉死：`GCS_CURSORPOS` 给的是**字节**偏移，「中」占 3 字节，
换算必须在多字节字符中间向外夹紧（`AGENTS.md:397-399`）。
端到端实测通过：微软拼音逐键推进 `z → zh → zho → zhon → zhong`，组合串带下划线渲染，
与已提交文本视觉分明（`README.md:175-179`）。

**这是「我们知道自己写了什么」的典型**：C# 侧拿到的是平台黑箱（能用，但组合/提交的边界语义不可见、
不可断言）；Rust 侧能断言、能单测、能解释每一次异常。

**(b) 诊断可被外部进程读取并自动断言 —— 这一条比 C# 侧强。**

`ShellState::publish_title`（`platform/mod.rs:95-107`）把
`committed={} chars={} app_events={} composing={}` 写进**窗口标题**，于是「提交链路是否通」
成为可由 `input-probe` 自动读取的量。`:88-91` 的注释把这个理由写得很清楚：
「人工验证一次只产出一个布尔值且不可复现；可读取的状态则能被反复验证」。
`chars_received` → `app_events` → 应用状态三层计数（`:49-61`）能区分
「消息没到」「到了没转发」「转发了没生效」—— C# 侧要拿同样的证据得挂调试器。

**(c) 中心化重绘门控在结构上排除了一类缺陷。**

`App::needs_redraw()`（`app.rs:156-163`）是唯一判据，外壳在消息循环末尾统一检查
（`platform/mod.rs:706-711`）。`app.rs:156-160` 的注释：**「这是 Arc Deck 的中心化重绘门控 ——
所有动画都汇总到这一处判断，于是「新增了一个动画却忘了请求重绘」这类缺陷在结构上不可能发生」**。
这是从一个真实事故反推的设计（`docs/ARCHITECTURE.md:63-72`：PezMax-One 让每个动画各自
`request_repaint`，一个 GIF 头像导致空闲时全屏 60fps 空转）。

**(d) 设计正典在命令模型里是「结构性成立」而非纪律。**

`SceneCommand` 只有 8 个变体且**刻意只有八个**（`scene.rs:141-205`）：无渐变变体
（「无渐变」在类型上不可能）、无阴影、无圆角（`FillRect`/`StrokeRect` 没有 `radius` 字段，
`:146-148` 解释了为什么：不让 99% 的调用点携带一个恒为 0 的参数）。
同一思路在 Kanesumi 侧对应 `CornerRadius` 三值枚举 + `SceneCommand` 八变体。
C# 侧这条只能靠纪律（`AGENTS.md` U1/U3 反复强调「不要覆盖模板」「不要换图标字体」）。

**(e) 骨架期的诚实记录密度极高。**

`docs/ARCHITECTURE.md:131-141`「已知缺口」逐条列出未实现项（`Arc`/`Triangle`/`Image` 未实现、
裁剪为空、`HeuristicTextEngine` 是占位、光标常亮、无障碍完全没有）；
`platform/mod.rs:155-156` 注释「未实现的命令在此**静默跳过**，并由调用方通过日志暴露 ——
**明确留缺口，好过假装画了**」；`:215-234` 的 `log_once` 只在缺口数变化时提示一次。
`AGENTS.md:344-347` 通用铁律 2 直接写着「**不假装做了**」。
对照 C# 侧曾发生的事故（`AGENTS.md:713-727`：3 个资源键从未定义、56 处引用**静默回退**、
编译器与运行时都不报错），这条纪律的价值是实打实的。

**(f) 类型级安全边界。**

`AGENTS.md:367-370` K2 把**全仓唯一允许裸 FFI 的地方**收敛到
`platform/win32.rs`（实测 54 行），`platform/mod.rs` 只做事件翻译与生命周期。
C# 侧没有等价约束。

### 5.3 一句话

> Rust 侧在**「可断言、可解释、结构上排除整类缺陷」**这件事上明确更强；
> 它弱的是**「把已经想到的东西铺满屏幕」**。前者是框架质量问题，后者是工程量问题 ——
> 而「C# 更舒服」感受的是后者。
