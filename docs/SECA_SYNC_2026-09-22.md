# 跨扇区对照与回流计划（2026-09-22）

> **背景**：Ether 扇区（本仓，Rust）与 Android 扇区 `GuitaristRin/Kanesumi-sec-a`（Kotlin/Compose）
> 共用同名同层骨架（`kanesumi-core` / `-anim` / `-structure` / `-controls`，参 `Ether/docs/PLAN.md` §6.2）。
> 本次在 Windows 侧把 sec-a 完整读了一遍（三份原始报告见 `docs/research/2026-09-22_seca_*.md`），
> 结论是：**回流是双向的，而且不是「谁抄谁」，是「谁那边有依据」**。
>
> 本文件是**跨扇区对照的入口**：现状差异、可回流清单、反向输出清单、待裁定项。
> 数值依据仍以本仓 `UWP_PRIMARY_SOURCES.md` 与 `CONTROL_SPEC.md` 为准；sec-a 侧没有任何一手源。

## §Ⅰ 一句话结论

| 方向 | 内容 | 依据强度 |
|---|---|---|
| **sec-a → 本仓** | 滑块的**分量比例**（thumb/行程）、释放决策的**位移宽容带**、单一 progress 同驱全部视觉、协调栈（多浮层共享预留）、极简填充式输入框范式、fling 手感数值表 | 手感经验（无一手源，属判断） |
| **本仓 → sec-a** | 动画时长（sec-a 三个时长正是我们今天用一手源推翻的旧值）、`cancel()` 取消语义、绝对位移拖动映射、Header+OnContent/OffContent 布局、令牌纪律 | **一手源**（UWP SDK / WinUI 字典） |
| **本仓内部** | 「断点表」的真相在**本仓自己**（`settings/src/kanesumi_window.rs` 720/640/320 + `navigation_view.rs` 320/48），应上提到 `kanesumi-structure` | 本仓既有实现 |
| **各自保留** | 本仓控件完整度（TextBox 893 行 vs sec-a 80 行）；sec-a 的 `LocalIndication` 注入、`MetroBottomStack` 生命周期 | 平台不同 |

**方法论**：本次三份报告都用「两侧 `文件:行号` + 照抄原行」的方式对照 —— 这是唯一能防止
「凭印象说哪边更好」的办法，建议固化为每次跨版本回顾的做法。

## §Ⅱ 滑动开关（用户点名的那个）

### 好在哪（三条机制，不是外观细节）

1. **滑块分量给足了**：sec-a thumb **22dp / 轨道 28dp = 78.6%**，左右仅留 3dp；行程 **24dp**
   （`MetroSwitch.kt:89,145-146`）。本仓 Capsule 是 knob 10 / 轨道 20 = **50%**、留白 5px ——
   滑块像「轨道里一颗小珠子」。这是「手感」最大的来源。
2. **释放决策两档宽容**（`MetroSwitch.kt:118-125`）：位移 < 15% 行程 → 当点动（翻转）；
   ≥ 15% → 就近吸附。解决「按下后微抖/拖回起点再松手」被判成拖动而原地不动
   （用户观感：「点了没反应」）。
3. **单一 progress 同驱全部视觉**（`MetroSwitch.kt:137-152`）：轨道填充、描边、滑块位置、
   滑块色全部读同一个 `progress` 并在 draw phase 取；220ms 一次收束，**无中间硬切换**。
   本仓是「三档布尔硬切」（ON 实心 / OFF 描边 / Pressed 中灰，`switch.rs` compute_colors）。

### 本仓反超、回流时勿改掉的 4 项

| 项 | 本仓 | sec-a |
|---|---|---|
| 拖动映射 | **绝对位移**（`start_progress + dx/travel`，丢帧也不漂） | 逐事件累加 delta（丢帧会漂） |
| 取消语义 | 有 `cancel()`（按下后移出轨道释放 → 不 commit） | **完全没有** |
| 拖动中按压视觉 | 有（Pressed 灰调，且只在真拖动时出现，避免点动闪灰） | 无 |
| 布局三件套 | Header + Track + On/OffContent（UWP 形态） | 无（标签由调用方外拼） |

### 本次已回流（2026-09-22）

1. **释放决策两档规则** → `switch.rs` 新增 `TAP_INTENT_MAX_DISPLACEMENT = 0.15` +
   `DragState.start_checked`（语义端点而非动画中位），3 个回归测试；
   与 UWP「拖出去再拖回来 = 取消」**不同**，属有意偏离（桌面鼠标下「点了没反应」更难受）。
2. **行程按一手源更正**：Capsule 留白 5 → **3**，行程 20 → **24**
   —— 一手源是 OS 模板写死的 `KnobTranslateTransform To="24"`（`generic.xaml` L13069-13072）。
   顺带发现旧注释把「垂直居中的 5px」当成了左右留白。
3. **令牌卫生**：ON 态悬停由手算 `primary.lerp(WHITE, 0.15)` 改为 `colors.primary_hover`
   （强调色派生档，单一真源）。

### 待裁定

- **U1 尺寸**：52×28 + 78.6% 滑块（sec-a 手感）vs 40×20 + 50% 滑块（本仓，有一手源
  `ToggleSwitch_themeresources_v1.xaml`）。建议**加形态变体**而不是替换：UWP 保真与触屏手感
  都是正当诉求，且本仓 `SwitchShape` 已经是枚举。
- **U2 时长**：220ms（sec-a，**无依据**）vs 150ms（本仓，`RepositionThemeAnimation` 惯例）。
  倾向 sec-a 向本仓对齐 —— 注意 UWP 模板里 knob 位移走的是**无参** `RepositionThemeAnimation`，
  时长 OS 预置、XAML 读不到，故 150ms 也属「惯例」而非实测。
- **U3 滑块颜色**：sec-a 用 `onPrimary`（其调色板下为白）；本仓 `Color::WHITE` 是**刻意的**
  —— 本仓 `on_primary` 对橙金 accent 判为黑（`Accent::most_readable_on`），
  用在**透明底的 OFF 态**会变成「黑滑块画在深底上」。故不能照搬，需先决定 OFF 态滑块语义。

## §Ⅲ 输入框族

### 关键事实：sec-a 的输入框「几乎无实现可搬」

`MetroTextField.kt` 全文 **80 行**（`:53-79` 就是 `Box.background().padding(12dp)` +
`BasicTextField`）：无边框、无状态机、无选区、无光标逻辑、无删除键、无 preedit。
本仓 `text_box.rs` **893 行**（其中渲染 518 行）。差距全在「Compose 框架免费提供的编辑内核」，
那部分**不可翻译，只能自造**（本仓已经自造了）。

**并且 `MetroTextField` 在 sec-a 是死代码**：唯一调用者是 `MetroChatInputBar.kt:61`，
`sample/MainActivity.kt` 零命中，全仓无 `KeyboardOptions`/`imePadding`/`focusRequester`。
所以「输入框挺舒服」是对**观感**的评价（一个纯色矩形 + 只有光标作状态反馈、无浮动标签、
无边框状态机），不是对已验证行为的评价。

### 值得搬的是「判断」而非「实现」

> **⚠ 2026-09-22 二轮更正（跨仓侦察，Sakichan）**：本节原先两条结论**范围写错了**，已按实测改：
> 1. 原文称「发送键硬门 `enabled && text.isNotBlank()`」是「唯一可直接翻译的策略」——
>    **反了，这是反向教训**：它在其唯一下游（Sakichan）造成功能死路。
>    `ChatScreen.kt:102` 在任务运行中把「发送」换成「中止」（图标同时换成 Close），
>    而 `MetroChatInputBar.kt:73` 的硬门控 + `MetroIconButton.kt:31` 的 `clickable(enabled=)`
>    ⇒ **输入框为空时中止按钮不可点**。门控属产品策略，已写成契约
>    （`docs/COMPOSITION.md` §11：控件不得内嵌产品策略）。
> 2. 原文称「`MetroTextField` 在 sec-a 是死代码」——**仓内成立、跨仓读会误导**：
>    下游 Sakichan 有 3 个调用点、2 种形态（`ConnectionScreen.kt:105` 服务器地址、
>    `SettingsScreen.kt:70` API Key，**均为单行 + 填充式**）。这**加强**了下方 `filled()` 变体的必要性
>    （从「可加可不加」变成「真实用例已有 3 处」）。

1. **极简填充式变体**：`containerColor = surfaceVariant`、直角、无边框、placeholder 不参与
   输入布局、**光标用 accent**（`MetroTextField.kt:47-48,59-65,77`）。本仓可加
   `MetroTextBox::filled()` 变体 —— 与「Kanesumi 直角铁律」比 2px 边框更贴，且是**加法**，不动现有观感。
2. **多行三元组**（唯一完整范式）：`min 40dp / maxLines 5 / 按宽算高`
   （`MetroChatInputBar.kt:64-71`）。本仓 `TextLayoutOptions{max_lines, wrap}` 与 `layout_box`
   已就绪（`kanesumi-canvas/src/text.rs`），但 TextBox 头部即声明单行。
3. **发送键硬门**：`enabled && text.isNotBlank()` + 图标/文字双形态
   （`MetroChatInputBar.kt:73-91`）—— 唯一可直接翻译的策略。

### 本次已修：对照中发现的主仓真 bug

**`MetroTextBox::ensure_caret_visible()` 是个空壳**（只 `reset_blink()`），`scroll` 字段
**没有任何写入者** ⇒ 单行输入一旦超宽，文本被省略号截断、光标停在右缘，
**用户看不见自己在打什么**；且渲染**完全没有 `push_clip`**（`COMPOSITION.md` 强制契约），
选区块与 preedit 虚线下划线可以画出框外（文本本身因默认省略号侥幸不出框，故长期未被发现）。

修法（同仓 `auto_suggest_box.rs` 早有正解）：渲染前按「光标必须可见」推进滚动并夹到
`[0, 文本宽 − 视口宽]`，内容区成对 `push_clip/pop_clip`；`render` 相应取 `&mut self`
（`PasswordBox` 委托签名同步）。新增 2 个回归（超宽必滚 + 装得下不滚 + 裁剪成对）。

### 引以为戒（报告并列出的同型病）

- sec-a：`MetroInsets.ime` 读了却无人消费 ⇒ 软键盘弹出时输入条不上移；`MetroDrawer` 拖拽关闭
  「明知需要却没做」。
- 本仓：`text_box.rs` 的 `show_delete` 永不出现在 Gallery、`min_height()` 无调用点、
  **Gallery 从不触发 TextBox 的 Hover 态**（`gallery/src/app.rs:1097-1117` 的 match 不含
  `Target::TextBox`）⇒ 今天刚按一手源改对的悬停边框**当前不可见**。

## §Ⅳ 构图 / 壳层 / 响应式

### 三个推翻预设的发现

1. **sec-a 没有断点表**（全仓 `600.dp|840.dp|WindowSizeClass|breakpoint` 零命中）。
   真正的断点表在**本仓自己**：`settings/src/kanesumi_window.rs`
   （`EXPANDED_BREAKPOINT = 720`、`>= 640` 换 padding、`height < 320` 转紧凑）+
   `navigation_view.rs`（`NAV_PANE_EXPANDED = 320` / `NAV_PANE_COMPACT = 48`）。
   ⇒ 「响应式」这一项的**回流方向是主仓内部上提**（settings → `kanesumi-structure`），
   并让 sec-a 来对齐。
2. **sec-a 没有形态切换器**：`MetroSidebar` 是死代码（唯一引用是它自己的 KDoc），
   sample 只用 `MetroShell + MetroBottomNav`。
3. **`MetroTopScrim` 用真渐变**（`Brush.verticalGradient`，120dp/alpha 0.55）——
   与铁律 6「无 ripple、无渐变、无阴影」冲突；本仓 `Scene` 也**没有渐变原语**
   （只有 FillRect/StrokeRect/Text/Arc/PushClip/Image/Triangle）。若要照搬，
   须按 `CONTROL_SPEC` §? 已有的「阶梯色带」先例改成 N 段纯色 FillRect。

### 值得搬的协调机制（不是外观）

`MetroBottomStack`（`kanesumi-core/.../insets/MetroBottomStack.kt:16-64`）：
底部各浮层（底栏 / mini player …）用 `rememberBottomStackReservation(key, height)` 把**自己的高度**
登记进共享表，**离开时自动注销**；可滚动内容用 `bottomOverlayPadding()` 自动留白。
作用域由 `MetroShell` 安装，**作用域外调用会按设计崩溃**（错误信息直接告诉你包哪一层）。

⇒ 这是一条可移植的「多浮层共同让出内容空间」契约。本仓对应问题（Dock 与通知/启动器
浮层如何共同预留）目前靠 layer-shell exclusive zone **按 surface** 解决；**应用级**（gallery /
launcher 内部）没有等价机制。建议按 §3(a) 清单落地（1 人日级）。

### `MetroShell` 的构图立场（与 M2 直接相关）

`MetroShell.kt:14-31` 只做三件事：装 bottom-stack 作用域、铺底色、把 `bottomBar` 作为
**overlay 画在 content 之上**（内容铺满全屏、自己留白）—— 并**明确点名拒绝** M3 Scaffold 的
「把底栏从内容空间切出来」；**不管 topBar**：「顶栏 = 页面第一个可滚动元素，不是 chrome」，
`MetroAppBar` 直接当 LazyColumn 的第一项。

`KANESUMI_DESIGN.md` 已明文背书 overlay 立场。本仓 `kanesumi-structure/src/layout.rs` 仍是
split（切 48px）。**这属 M2-1 之前的契约裁定**：改 overlay 要连带重算 `layout.rs` 的 4 个测试、
`lib.rs` 的 AppBar 宿主，并回答「`ShellLayout.app_bar` 存废」（会与 settings/librarian
现有固定 AppBar 用法冲突）。列为待裁定，不在本轮擅改。

### 顺带修掉的溯源错误

本仓 3 处注释写「纯色无渐变（参 **SD §II**）」，但 `compositor/docs/SD.md` **全文不含「渐变」二字**
（§II 讲的是空间结构 Top Bar/Dock/Launchpad）。正确出处是 `KANESUMI_DESIGN.md` §Ⅲ.1 铁律 6（L102）
与 L77。已改 `scene.rs` / `color.rs` / `harness/render.rs`。
> 之所以要改：`MetroTopScrim` 那条「scrim 要不要梯度」的裁定，其依据链正挂在这个错误溯源上。

## §Ⅵ 这轮对照对「多端同步」的价值

1. **同层骨架 + 同名 API 是对的**：三份报告都能做到「同名文件对同名文件」地比，
   否则跨语言根本无法对照。
2. **「默认即正确」的机制值得本仓学**：sec-a 把交互反馈装进主题层
   （`MetroTheme` 注入 `LocalIndication = MetroIndication(pressTint)`），
   于是**任何 `.clickable{}` 免费获得直角闪切**（按下 100ms 淡入 / 松手 200ms 淡出，
   零重组）。本仓的按压反馈目前是**每个控件各写一遍** —— 这是 M1「保险机制」思路的更彻底版本，
   可考虑在 `decl.rs` 的 reconciler 层做等价物（命中表已知被按下的叶子，渲染后统一叠一层 press tint）。
3. **同步要有「单向源」的概念**：凡有 UWP 一手源的项（时长、色值、几何）**一律以本仓为准**，
   sec-a 跟随；凡属平台手感经验的项（滑块比例、fling 数值、insets 抽象）**双向流动**。
   把这条写进 PLAN.md 的扇区章节，比每次重新讨论省事。
4. **定期做一次「对照审计」**：本次的产出方式（三份带 `文件:行号` 的报告 + 一份结论）
   可以直接复用到 sec-w 等未来扇区。
